LibTrack AI — Project Overview

Purpose: Detect library/language/tool releases and planned future versions, summarize changes, and notify project teams by email. Uses official registries when available, with a Serper+Groq fallback for web analysis.

High-level architecture

  • Data Store: Django models (SQLite by default in this repo).
  • Detection Engine: tracker.management.commands.run_daily_check coordinates detection.
  • Fetchers & Analyzers: Registry helpers in tracker/utils (official API helpers, serper_fetcher, groq_analyzer).
  • Notification: HTML emails via Mailtrap / Sender implemented in tracker/utils/send_mail.py.
  • User-facing: Django templates and views under tracker/templates/tracker and tracker/views.py.

Core features

  • Project registration with team emails and tech-stack components.
  • Central Library entities to minimize repeated API calls.
  • Release detection (official registries preferred).
  • Future/planned version detection (roadmap/beta/RC) using web search + Groq.
  • Per-project notification rules: major/minor/future.
  • History of releases and future update lifecycle tracking.

Key data models (summary)

ModelPurpose
ProjectRegistered projects and team contact info.
StackComponentComponents declared by a project; linked to Library where possible.
LibraryCanonical library/tool record to reduce duplicate API calls.
LibraryReleaseHistory of releases for a library.
UpdateCacheRecently detected released updates per project.
FutureUpdateCacheDetected future/planned versions, confidence, status (detected/confirmed/released/cancelled).

Detection & run_daily_check flow

  1. Sync Libraries: Link unlinked StackComponents to Library rows (_sync_libraries()).
  2. Fetch Updates: For each unique Library, call official registry APIs (if enabled) via LibraryUpdateHelper; otherwise use Serper + Groq fallback (serper_fetcher + groq_analyzer).
  3. Analyze results: Groq returns a structured JSON hint (version, category, is_released, confidence, expected_date, summary).
  4. Handle future updates: _handle_future_update() saves candidates into FutureUpdateCache when confidence >= threshold (default 70) and user opted in.
  5. Notify Projects: For each Project subscribed to relevant categories, assemble HTML email payload and call send_update_email().

Future version lifecycle

States: detected → confirmed → released (or cancelled). Transition triggers:

  • Detected: Automated detection via Groq/Serper or registry pre-release
  • Confirmed: Manual via Django admin or API—update confidence and status
  • Released: Auto-promoted when a subsequent run detects the version as officially released
  • Cancelled: Manual change when roadmap or announcement is withdrawn

Where implementations live (important files)

  • tracker/management/commands/run_daily_check.py — Orchestrator for sync, fetch, notify.
  • tracker/utils/library_update_helper.py — Official registry API logic and adapters.
  • tracker/utils/serper_fetcher.py — Web search wrapper (Serper.dev).
  • tracker/utils/groq_analyzer.py — Groq prompt + JSON parsing and heuristics.

Configuration & running

  • Set environment in .env (Mailtrap keys, USE_OFFICIAL_APIS, SERPER url, Groq keys etc.).
  • Run once with: python manage.py run_daily_check. Use --auto --time HH:MM to schedule daily runs.

Testing

  • Unit tests are under tests/ and some tracker tests in tracker/tests.py.
  • Use pytest -q to run tests locally.

Implementation notes & important heuristics

  • Groq is configured to always return strict JSON using a guided system prompt and schema hints.
  • Priority for sources: registries (npm/pypi) → GitHub releases → official docs → reputable sites.
  • Confidence scores drive whether future updates are saved and whether notifications are sent (default threshold 70%).
  • Libraries are deduplicated and linked to StackComponents to limit API calls.
